Diagrammes d’architecture logicielle

Décrivez les personnes, applications, services et bases de données d’un système et les appels entre eux. skemo place chaque boîte, trace chaque flèche et garde le dessin net quand le système évolue.

Comment l’écrire

  • Une carte par brique : card#api.app API. L’#id la nomme pour les flèches, la classe lui donne un type.
  • Une zone par frontière : un système, une équipe, une unité de déploiement. Ce qui est indenté sous la zone est dedans.
  • Les flèches s’écrivent dans la carte qu’elles quittent : to(db) SQL sous le service commandes dessine l’appel et son étiquette. to(catalog orders) dessine deux flèches qui partagent une fourche.
  • Les types sont du CSS : .app { --c: #3E6FC4; --label: "Conteneur"; } colore tous les conteneurs et écrit leur catégorie au-dessus du nom. Une ligne à changer pour restyler tout le diagramme.

Le modèle C4

L’exemple suit le niveau conteneurs du modèle C4 : une personne, les conteneurs d’un système, un système externe. Chaque niveau C4 est un fichier .skemo distinct, avec les mêmes types :

Niveau C4Dans skemo
Contexteune carte par système et par type d’utilisateur ; votre système en une seule carte
Conteneursvotre système en zone, avec ses applications et ses bases
Composantsun conteneur en zone, avec ses composants
Déploiementdes zones imbriquées pour les régions, les réseaux et les machines : voir cloud et réseau

Rester lisible

  • Choisissez la direction du flux principal : diagram(dir="down") pour le parcours d’une requête, dir="right" pour une chaîne de données (Placement).
  • Donnez aux flux asynchrones leur propre classe de flèche (.async, en tirets) pour qu’ils se lisent sans couleur.
  • Ajoutez une légende qui liste les types pour vous : card.legend(at="ne") (Cartes enrichies).
  • Modifiez librement : ajouter un service refait le placement, et épingler une carte avec at="x,y" la garde où vous voulez.

Arrows

An arrow is written inside the card it leaves: to(target). Its classes style it, its text labels it.

Writing an arrow

card#api API
  to(db)                      //- api → db
  to(queue).dashed events     //- styled, with a label
card#db Database
card#queue Queue

The target is the #id of a card. An unknown target is an error, with a suggestion when the id is close to an existing one. Arrows may go backwards, form cycles, or link a card to several others.

Styles

ClassEffect
.dashed, .dotteddashed or dotted line
.thickthicker line

.noheadno head
.dota dot at the start
.linkdotted, no head: attaches a note to a card
.wan, .securecolour examples of the default theme (red and thicker, green)

Classes combine (to(b).dashed.both). Your own classes colour arrows through CSS: .edge.important { color: #E8590C; }. When the direction or the kind of an arrow matters, give it a line style too, not only a colour, so it reads in black and white.

Several targets

to(w1 w2 w3) creates one arrow per target, all with the same classes and label (a label is therefore repeated on each arrow).

Shared trunk

With join="trunk", the arrows of one to(…) leave the same point and share a trunk before branching, the way organisation charts are drawn. Each target still has its own arrow, with its own id and animation marker.

(preview) Plain arrows from one card to several cards of the next row are drawn this way without asking (a fork). When several cards each link to the same cards of the next row, every one to every one, their arrows share one bar between the rows (a bus) instead of crossing. Junctions are marked with a dot.

(preview) Any other name joins arrows into one card: arrows to the same card that carry the same join="http", written under different cards, meet before it and end on one line with a single head (the HTTP calls of two frontends to one backend, in the Kubernetes example of Layout). A name that no other arrow to that card carries is reported and ignored. Their label names the whole flow: it sits on the part the arrows share, just before the card.

A line without a head (.nohead, .link, a head shown as a dot) runs right up to the card.

Arrows outside the layout (preview)

constraint="false" draws and routes an arrow without letting it shape the layout: its target is not pushed a row further. Use it for cross links (service discovery, monitoring, callbacks) that would otherwise turn the diagram into a long chain. Here CoreDNS stays beside the pods instead of below them.

Classes from the endpoints

Every arrow automatically receives the classes from-<type> and to-<type> of the cards it joins, so one CSS rule can colour all arrows leaving or entering a type.

Sides, waypoints, ids

AttributeEffect
side="right-top"attachment side at the start and at the end, among top bottom left right. One half may stay empty: side="-top"
via="x,y x,y"waypoints the route passes through, in order
href="…"the arrow is a link (SVG and HTML)
to#id(…)an explicit id; by default an arrow is called source->target (then #2, #3 for duplicates)

See Layout and positions for when to use side and via.

Routing

Every arrow is routed with right angles, around the cards and around the zones that contain neither of its ends. Bends sit in the middle of the free corridor, and arrows that share a side are spread apart. You never draw a route yourself.

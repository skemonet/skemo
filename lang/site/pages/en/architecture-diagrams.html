Software architecture diagrams

Describe the people, applications, services and data stores of a system and the calls between them. skemo places every box, routes every arrow and keeps the drawing tidy when the system changes.

How it is written

  • One card per building block: card#api.app API. The #id names it for arrows, the class gives it a type.
  • One zone per boundary: a system, a team, a deployment unit. What is indented under the zone is inside it.
  • Arrows are written inside the card they leave: to(db) SQL under the Orders service draws the call and its label. to(catalog orders) draws two arrows that share a fork.
  • Types are CSS: .app { --c: #3E6FC4; --label: "Container"; } colours every container and writes its category above the name. Change one line to restyle the whole diagram.

The C4 model

The example follows the container level of the C4 model: a person, the containers of one system, an external system. Each C4 level is a separate .skemo file with the same types:

C4 levelIn skemo
System contextone card per system and per kind of user; your system as a single card
Containeryour system as a zone holding its applications and data stores
Componentone container as a zone holding its components
Deploymentnested zones for regions, networks and machines: see cloud and network diagrams

Keeping it readable

  • Choose the direction that follows the main flow: diagram(dir="down") for request paths, dir="right" for data pipelines (Layout).
  • Give asynchronous flows their own arrow class (.async, dashed) so they read without colour.
  • Add a legend that lists the types for you: card.legend(at="ne") (Rich cards).
  • Edit freely: adding a service re-lays out the diagram, and pinning a card with at="x,y" keeps it where you want it.
